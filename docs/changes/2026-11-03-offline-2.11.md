# Offline Android 2.11.0 — prepared for publication

Prepared on 2026-11-03 from master `6774ad3a9589f0e91b303fd1ee1f1b6cede7b17b`. No source push or live deployment has been performed for this candidate.

## Included changes

The offline WebAssembly client is rebuilt from the current shared Panel pages, models, services, scoped styles and assets. This includes the seven export destinations (including Lebanon), compact warehouse transfers, complete passport history, export sales financial form, mobile action placement, numeric-input handling and lookup-cache performance changes. The separate online Android package is unchanged.

New local adapters and server receipt handlers cover daily work plans and one-day exceptions, legacy instrument registration, hall-service profit payments and profit-rule edits. Pending work-plan/rule revisions and newly imported bowl/assembly IDs resolve through durable receipt aliases before later operations. Legacy imports preserve historical performers and do not consume raw stock. Production completed while offline contributes to the work-plan report using Tehran's day boundaries. New server capabilities are included in the snapshot; old snapshots cannot silently queue unsupported new actions.

Workspace fingerprint compatibility is preserved: the new work-plan section and capability metadata are outside the legacy hash. Work-plan revisions still enforce their own concurrency checks. No new database migration, local SQLite version change, package ID change or encryption-key alias change is introduced.

Old offline shipments with Persian/free-text shipping methods are replay-compatible with the current financial sale controller. Sale-event metadata, actual accounting/profit dates and idempotent operation receipts are retained.

Android's default AAPT ignore pattern silently excluded `_framework` from the APK. The packaging pattern now includes Blazor's runtime directory. The signed APK verifier checks every packaged panel file against the published source, not merely the source directory. CI now also checks the actual APK bundle after assembly.

## Publication order

1. Publish this tested source to master only when the user requests publication. Follow the root AGENTS.md: Liara's native GitHub integrations own deployment of both panel and API; preserve their service selectors and private settings.
2. Verify the deployed commit and health for both services. This change needs no additional schema migration relative to the current master baseline.
3. Verify an authenticated snapshot exposes `workPlans` and `offlineCapabilities` before distributing the APK as a live update.
4. Install the APK over the existing offline app. Do not uninstall or clear its data. Existing encrypted snapshot and pending queue must remain intact.
5. Connect once and let pending operations synchronize, then receive the new snapshot before using the newly added offline actions. A snapshot is not replaced while unsent/conflicting entries remain; resolve those through the existing review flow.
6. On the administrator phone, test restart and airplane mode, a production stage and work-plan edit, reconnect and verify a single server result. Keep the old APK and previous Liara release for rollback; never downgrade or uninstall a phone with unsynchronized work.

Password changes, Telegram delivery, remote warranty activation, push enrollment and a complete server database backup still require network/server access. Local production, work plans, inventory, sales and the supported management operations persist on the phone and synchronize later.
