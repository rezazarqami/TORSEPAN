# Single-phone offline production — prepared, not published

The Android 1.2 source includes a separate, bundled local interface. The current Blazor Server panel remains online; caching its HTML would not make its event handlers work offline.

## Combined test release scope

- One administrator account registers one phone while connected. A complete initial snapshot must finish before offline work can begin. No internet or advance warning is needed to open the already prepared local interface later.
- An always-available native toolbar opens the local screen after confirming the phone's screen-lock credential. Search accepts Persian/Arabic digits and instrument or bowl codes. It displays the most recently received passport and locally queued stages.
- Supported mutations: new bowl creation, dimple, shape including stretch/note-area/edit contributors and custom scales, bake, normal/export tune, glue/assembly, exit glue room, final tune, QC approval/rejection, internal/export packaging, export routing and shipment, stock receipt/absolute correction, sale, production/instrument notes, design registration, passport scale/performer corrections and photo upload. A bottom without notes starts at bake and skips tune, exactly as online. Top/bottom histories and actual performers remain separate.
- New bowls use the operator's actual unique production code. Local duplicate codes are rejected; server duplicates stop sync for review instead of replacing records. Code-based administrative scale edits also work for a locally created bowl whose server ID is not yet downloaded.
- Stock, design types, active accounting parties and sales attribution options are cached with the passport snapshot. Material consumption is projected locally; every material has a concurrency token and its own receipt dependency chain across different bowls/packaging operations. Packaging preserves the exclusive case rule and consumes two triangular items, matching the online command.
- Sales create accounting revenue/payment records and retain the actual offline sale/warranty date. Remote warranty activation has a durable server retry marker and runs after the sale transaction commits. External service availability does not decide whether the sale was saved.
- The native offline photo picker uses Android's document picker and ImageDecoder (including supported HEIF inputs), produces JPEG/thumbnail and a SHA-256 checksum, then encrypts the complete upload in SQLite before reporting success. Retries use the same operation ID and payload on a separate bounded API route. Pending thumbnail previews remain available until the authoritative refresh. Previously uploaded full-resolution images are not included in the local snapshot; the existing server photo gallery remains the source of those images.
- Inventory browsing groups local instruments/bowls by stage, including QC, packaging, warehouse and sold goods. These numbers reflect the last snapshot plus this phone’s queue, and are not live server values while disconnected. Payroll, messaging, order management and backup generation are outside this production offline workflow.
- Each local write is committed to the app's private SQLite outbox before the interface reports success. Tokens, snapshots, request payloads and queue messages are encrypted using an AndroidKeyStore AES-GCM key. The local WebView serves only four bundled assets, blocks remote resources and has no credential-reading bridge. The normal photo picker/PDF/download code remains in the online WebView.
- Foreground polling checks for the designated account's online token and syncs every 30 seconds. Android JobScheduler maintains a persisted network-dependent outbox job and a periodic 15-minute job; Android may defer background work for battery/network policy. Opening the app or pressing the sync button tries immediately. Jobs are not an exact wall-clock guarantee, and force-stopping the app suppresses background work until reopening.
- Login/logout or account changes cannot replace another account's cache or erase its queue. Logging out pauses new local writes and submission; logging back into the designated administrator account resumes them. Expired/revoked server credentials require login before sending. Device data remains visible only after the phone credential check. The server rechecks administrator access, enrollment and current performer roles on every request.
- Event times use the last received server clock anchored to Android's monotonic elapsed time within the same boot, with a wall-clock offset fallback after reboot. The server rejects implausible dates; it does not replace actual operation time with sync time. Large clock changes after reboot can require review.

## Sync and conflicts

The phone generates a stable UUID once per operation and sends the stored request unchanged on retry. The API commits the existing business command and its receipt in one serializable database transaction. PostgreSQL serializes offline submissions with a transaction advisory lock. Retries of an already committed request return its original receipt; changed contents using the same UUID are rejected.

Every operation checks a fingerprint of both linked bowls, their instrument/assembly concurrency tokens and passport events. Sequential local changes refer to a prior receipt; glue checks both independent bowl chains. A competing online edit produces a conflict instead of overwriting either side. Application-managed CLR concurrency tokens also protect detached online repository updates against stale writes.

Successful queue entries stay available for local projection until a fresh authoritative snapshot is installed atomically. If communication fails after the server commits, the request ID and body remain in the queue for safe retry. Unsent or disputed operations prevent the base snapshot being replaced. A permanent validation/conflict error stops the queue and marks the operation for review; the queue UI retains the data and offers a retry of the same request after the online issue is resolved. There is deliberately no automatic discard, force overwrite or device transfer action. Reassigning performers or resolving a true stage divergence needs a supervised recovery flow before this can be treated as a full offline system.

## Preparation and release order

Nothing from this feature has been pushed or deployed. The user requested a change list before authorizing publication. Before release, synchronize API and panel changes onto their separate deployment branches while preserving their existing differences, verify PostgreSQL migration and real handset acceptance in isolated staging, then deploy both services before installing APK 1.2 on the designated phone. If the existing APK signing key is available, retain it for an in-place update. Do not uninstall an app with unsent offline entries just to change signing keys.

The migrations add OfflineDevices, OfflineReceipts, four OfflineVersion columns (bowls, assemblies, instruments and materials), plus a WarrantyPending receipt flag/index. Generated model metadata also reconciles historical snapshot omissions for already existing accounting/photo tables; it must not recreate those tables or drop their data. Android local database version 1 has no destructive upgrade path. Removing the app or clearing its data destroys unsent operations and its encryption key; server backups do not include that local outbox.

## Validation

- `dotnet run --project tests/WorkspaceSmoke -- --offline-only`: real command handlers against SQLite, paired chain through QC, timestamps/performers, idempotent retry, rollback, roles, clock validation, passport edits, detached concurrent update and PostgreSQL migration metadata.
- `npm ci --prefix tests/OfflineUi && npm test --prefix tests/OfflineUi`: bundled DOM scripts without server access, Persian lookup, sequential saves, form preservation and escaped histories.
- `node android/tests-offline.cjs`: local projection, paired stages/QC rejection, role/scale filtering and Persian code normalization.
- `gradle :app:testDebugUnitTest :app:assembleDebug`: Robolectric SQLite outbox reopening, paired dependencies, lost response retry, snapshot replacement guard, conflict preservation and account isolation; installable APK compilation. Host tests inject a fixture codec; real AndroidKeyStore and device credential prompts need handset staging acceptance.
- Existing export/production UI and manual-backup checks should run because concurrency tokens and snapshot transaction ownership affect those paths.

Live Liara deployment, actual phone screen-lock/WebView behavior, Android battery/job timing and a real airplane-mode scenario remain acceptance checks, not claims established by compilation or host tests.
